# Проверка применимости изменения через GigaChat

Точка входа: backend/app/services/law_relevance_service.py,
assess_law_change_relevance(change, interest, user_context="...").
Сервис не изменяет БД и не отправляет уведомления. Его внешняя сигнатура
и поля relevant/reason/status сохраняются для части уведомлений.

## Два этапа

1. analyze_law_change получает только заголовок, описание, доступные редакции
и дату изменения. Пользовательские сообщения на этот этап не передаются.
GigaChat выделяет конкретное изменение и обязательные условия затронутых групп.
Код проверяет структуру, уникальность идентификаторов и наличие цитат из закона.
Если содержание неизвестно, возвращается insufficient_data без второго этапа.

2. Модель получает фиксированные группы условий и сообщения пользователя.
Для каждого id она извлекает факт, цитату и оценку соответствия:
met / not_met / unknown. Пропуск, добавление и дублирование id запрещены.
Цитаты сверяются с контекстом с нормализацией только регистра и пробелов.
Модель не вычисляет итоговую релевантность.

Группы являются альтернативными (ИЛИ), условия внутри группы обязательны (И).
Хотя бы одна группа полностью выполнена → relevant.
Все группы явно исключены → irrelevant.
Остальные случаи → insufficient_data.
Ошибки соединения/формата → error.

На каждом этапе допустима одна попытка исправления формата: обычно два вызова
GigaChat, максимум четыре. Ошибки сети внутри проверки не повторяются.
Анализ закона выделен в отдельную функцию для будущего повторного использования;
сейчас он выполняется для каждой пары изменение/интерес, кэш ещё не подключён.

## Результат для уведомлений

| status | relevant | Действие |
| --- | --- | --- |
| relevant | true | Кандидат на уведомление |
| irrelevant | false | Не уведомлять |
| insufficient_data | false | Уточнить недостающие данные |
| error | false | Повторить проверку позже |

reason вычисляется из статуса и фактов пользователя, до 500 символов.
conditions содержит фиксированные требования закона и соответствующие факты,
оценки и цитаты пользователя. law_analysis содержит проверенный результат
первого этапа для аудита. Эти поля пока не сохраняются в БД автоматически.

Правильный формат и присутствие цитат не доказывают правильность смыслового
сопоставления или полноту условий. Оба этапа используют модель.

## Контекст

law_user_context.py собирает до 20 последних сообщений самого пользователя
из связанного чата, максимум 6000 символов. Проверяет владельца чата,
исключает ответы ассистента и сохраняет хронологию с приоритетом новых сообщений.
Это заявления пользователя, а не независимо проверенные факты.
При непустом user_context используется он; иначе source_excerpt.
Ключевые слова остаются предварительным фильтром в рассылке.

## Оценка

Из backend:
../.venv/Scripts/python.exe evaluate_law_relevance.py

10 вымышленных примеров: tests/fixtures/law_relevance_cases.json.
Это не действующие законы. Ожидаемые результаты заданы вручную.
Прогон не использует БД и не рассылает уведомления.
Отчёт: docs/law_relevance_evaluation.json; он включает оба этапа.
Исходный результат 3/6: docs/law_relevance_evaluation_baseline.json.
Последний результат объединённой проверки 6/10:
docs/law_relevance_evaluation_one_pass.json.

Набор использовался при разработке и не является независимой оценкой.
Один удачный прогон не доказывает устойчивость; требуется отдельный набор
и повторные проверки. Ошибки формата учитываются отдельно от неверных решений.

## JSON-схема и проверка полноты 09.10.2026

На предыдущем этапе проверялся response_format с JSON-схемой и strict=true.
Формат описан в официальной документации:
https://developers.sber.ru/docs/ru/gigachat/guides/structured-output
Это не заменяет Python-валидацию: текущий настроенный alias GigaChat
в реальном прогоне вернул недопустимый kind даже с указанной схемой.
Поддержка строгого соблюдения схемы текущим сочетанием модели и endpoint
не подтверждена. Модель и адрес API автоматически не менялись.

В 14 вымышленных сценариях добавлена ручная разметка expected_law:
отдельные признаки роли, деятельности, территории, порогов и альтернатив.
backend/law_evaluation_coverage.py проверяет количество групп и отдельных
условий, типы и наличие размеченных фрагментов. Это строгая проверка
структуры и лексических ориентиров, а не доказательство юридической
корректности; эквивалентная формулировка или объединение условий может
не пройти. Проверка применяется только в оценочном скрипте, не в рассылке.

Последний прогон --suite holdout заменяет предыдущие результаты этого набора:
3/4 совпадений итогового статуса; 1 ошибка первого этапа (Invalid condition kind);
0/4 разборов прошли строгую проверку покрытия. Ложных положительных
решений относительно ожидаемых статусов в этом прогоне нет.
Потребительский, кадровый и отраслевой примеры не прошли проверку
отдельных условий; пример альтернативных групп не дал валидного разбора.
Результаты: docs/law_relevance_evaluation_holdout.json.
Набор теперь используется для диагностики, поэтому его нельзя считать
независимым для дальнейшей настройки. Нужен новый контрольный набор.

40 целевых автоматических проверок прошли, включая передачу схемы через
HTTP, совместимость обычного чата и обнаружение пропущенных условий.
Следующий технический шаг: отдельно проверить поддержку structured output
текущим endpoint и моделью либо совместимый принудительный function calling.
Только после стабилизации формата стоит оценивать смысловую точность
на новых сценариях. Готовность к автоматической рассылке не подтверждена.


## Принудительная генерация аргументов функции

Текущий первый этап использует functions и function_call с именем
extract_law_conditions. Схема и два общих вымышленных примера находятся в
backend/app/services/law_analysis_schema.py. Пользовательские данные в них
и в запросе анализа закона отсутствуют. Второй этап использует функцию assess_user_conditions со схемой оценок.
Допустимые id формируются только из уже проверенного анализа закона.
Полноту набора, отсутствие повторов и наличие цитат проверяет Python-валидатор.

Клиент принимает аргументы функции как объект или JSON-строку. Имя функции
должно совпадать с запрошенным. Отсутствующая функция, чужое имя или неверный
тип аргументов приводят к ошибке, без перехода к свободному тексту. Сами
функции не исполняются: это транспорт структурированных данных. При повторе
валидации в историю передаётся JSON как текст, без function_call/state_id;
незавершённых вызовов функций в истории нет.

На коротком техническом запросе действующий endpoint вернул свободный текст
вместо JSON при response_format, но корректные аргументы при function_call.
Документированный api.giga.chat/v1/chat/completions вернул HTTP 404 для обоих
вариантов с текущими настройками. Рабочий endpoint и модель не менялись.
Источник протокола:
https://developers.sber.ru/docs/ru/gigachat/guides/functions/function-calling-modes

Первый диагностический прогон без примеров: 2/4 статусов, 0/4 покрытий,
ошибка цитаты на первом этапе и неверная логика альтернатив. Это показывает:
function calling сам по себе не доказывает полноту и правильность анализа.


Итоговый диагностический прогон после общих примеров и function calling
на обоих этапах: 3/4 статусов, 0 ошибок формата/валидации, 2/4 покрытий.
Сценарии с неизвестным числом работников и неподходящей деятельностью
прошли проверку покрытия. Потребительский пример остался с объединёнными
условиями, а альтернативные категории снова оказались в одной группе:
для человека с инвалидностью без статуса пенсионера получено неверное
irrelevant. Исправление транспорта не устраняет эту смысловую ошибку.
Это один диагностический прогон, а не подтверждение стабильности.
45 целевых автоматических тестов прошли.

Следующая работа: проверить извлечение альтернативных групп и атомарность
на отдельном новом наборе, затем решить, достаточно ли текущей модели.
Возможные изменения модели нужно оценивать отдельно вместе со стоимостью;
в текущем изменении модель, endpoint, уведомления и архитектура не менялись.

## Проверка логики на новых ситуациях

В промпте и описаниях полей явно разграничены И/ИЛИ, совместные роли и
повторение общего ограничения в каждой альтернативе. Изменения не включают
правила, распознающие конкретные слова закона. Добавлены регрессионные тесты
общей территории: она обязательна в каждой альтернативной группе.

Новый набор: backend/tests/fixtures/law_relevance_logic_validation.json.
Шесть вымышленных ситуаций: альтернативные роли с общей территорией,
совместные роли, неизвестное и неподходящее назначение помещения.
Запуск из backend:
../.venv/Scripts/python.exe evaluate_law_relevance.py --suite logic
Для изолированного сравнения доступен --model GigaChat-2.
Переопределение действует только в процессе оценки; .env не меняется.
Каждой модели соответствует отдельный файл отчёта.

Результаты после уточнения инструкции:
- GigaChat: 2/6 статусов, 3 ошибки валидации, 0/6 строгих покрытий.
- GigaChat-2: 2/6 статусов, 3 ошибки валидации, 0/6 строгих покрытий.
- GigaChat-2-Pro: все запросы завершились ошибками API; качество не оценено.
  Отдельный технический запрос подтвердил HTTP 402. Наличие модели в
  GET /models не гарантирует успешное выполнение запроса с текущим доступом.
  Для GigaChat-2 ответ API подтвердил model=GigaChat-2:2.0.28.2.

Старая и вторая модели снова ошиблись с альтернативами и объединением
условий. Отдельная экспериментальная сверка ошибочного черновика не
исправила альтернативу; дополнительный вызов не включён в рабочий сервис.
Диагностический ответ сохранён в docs/law_relevance_review_probe.json.
Промпт не считается исправлением смысловой ошибки.

Клиент теперь передаёт безопасный HTTP-статус через GigaChatAPIError;
сервис возвращает error_code вида HTTP 402 без тела внешнего ответа.
Ранее сохранённый отчёт Pro содержит RuntimeError, поскольку создан до
этого расширения диагностики. Ошибки API нельзя интерпретировать как
неверные решения модели. 50 целевых автоматических тестов прошли.

Рабочая модель и архитектура сохранены. Автоматическая релевантность
текущей модели не подтверждена. Следующий обоснованный шаг — обеспечить
успешный тестовый доступ к более сильной модели и прогнать тот же набор,
затем новый независимый набор. Без этого дальнейшее усложнение промпта
не даёт доказанного улучшения. Смену рабочей модели следует делать только
по результатам проверки точности, задержки и стоимости.

## Диагностика доступа к Pro

GET /api/v1/balance выполнен успешно (HTTP 200). Ответ содержит позиции
GigaChat и embeddings; отдельная позиция Pro отсутствует. Это не следует
записывать как доказанный числовой ноль: API её не вернул.
Безопасный снимок: docs/gigachat_access_diagnostic.json.

Запрос к GigaChat-2-Pro ранее вернул HTTP 402. По официальному описанию
эта ошибка означает, что закончились токены запрошенной модели:
https://developers.sber.ru/docs/ru/gigachat/api/errors-description
Документация баланса:
https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/get-balance

Сочетание HTTP 402 и отсутствующей позиции Pro указывает на ограничение
доступных токенов для этой модели. Остаток GigaChat не доказывает наличие
токенов Pro. Для продолжения нужно проверить лимит Pro в личном кабинете
именно проекта, которому принадлежат используемые API-ключи, и обеспечить
тестовый доступ к Pro. Наличие имени модели в /models этого не заменяет.
Причину отсутствия пакета/его расходования API баланса не сообщает.

После успешного доступа запуск из backend:
../.venv/Scripts/python.exe evaluate_law_relevance.py --suite logic --model GigaChat-2-Pro
Переключение модели в этом запуске изолировано от настроек приложения.
Менять промпт или OAuth-секреты для устранения HTTP 402 не требуется.
