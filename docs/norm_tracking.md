# Связь ответа ассистента с конкретной правовой нормой

## Текущий вариант: без обязательного каталога (11.10.2026)

Итог проверки: 211 backend-тестов прошли, 1 пропущен. Реальный GigaChat при отключённом RAG создал две связи с нормами; импорт ранее проверенной поправки дал одно уведомление, повторный запуск — ноль. Проверены событие Redis, REST, переход к истории чата, изоляция другого пользователя и отметка прочтения. Отчёт: `docs/notification_without_catalog.json`. Это проверка полной цепочки на примере, а не подтверждение охвата всех законов.

Связь сохраняется автоматически из цитаты в ответе: пользователь → чат → идентификатор исходного закона → статья/часть. Новые таблицы и ручная разметка не нужны. `answer_norms.py` распознаёт ТК РФ, статьи всех четырёх частей ГК РФ, Закон РФ «О защите прав потребителей» и законы/ФКЗ с номером и датой вида ДД.ММ.ГГГГ. Например: «часть 16 статьи 4 Федерального закона от 03.06.2009 № 103-ФЗ». Номер и дата дают ключ `ru:103-fz:2009-06-03`; номера статей разных законов не смешиваются. Неоднозначное «статья 10» не сохраняется. Для остальных кодексов нужны реквизиты исходного закона. Часть ГК определяется по диапазону нумерации статей; это не проверка существования статьи или правильности её применения. Произвольные формы цитирования пока не покрыты.

GigaChat получает инструкцию писать полные реквизиты использованных норм. Разбор выполняется также для ответа из кэша. Перед сохранением проверяется принадлежность чата и сообщений пользователю; свидетельство прямой цитаты восстанавливается из сохранённого ответа. Цитата подтверждает использование нормы в ответе, а не юридическую правильность совета или действительность редакции.

Мониторинг сохраняет идентичность исходного закона из датированного заголовка обзора Consultant. Для точной статьи по возможности разбирается публикация поправок и её ссылки. Каталог RAG остаётся необязательным источником текстов для ответов; он больше не ограничивает перечень отслеживаемых законов. Старые разделы ниже описывают прежние этапы и дополнительные режимы.

Если известна конкретная статья, уведомление получают чаты с этой статьёй/родительской нормой. Если обзор подтверждает только изменение закона, уведомление получают связанные с законом пользователи с явным пояснением: «Изменение конкретной статьи пока не подтверждено». Это намеренно более широкое предупреждение. Подтверждённая точная привязка впоследствии не расширяется из-за сетевой ошибки. После успешного уточнения временная привязка ко всему закону заменяется точной.

Уведомление сохраняется в БД до публикации Redis, содержит ссылки на связанные чаты и не повторяется для пары пользователь–изменение. Сбой Redis не удаляет запись: она доступна через REST. Постоянная доступность внешнего источника не гарантируется; мониторинг охватывает настроенные обзоры, а не всё законодательство России. Уведомления старше окна обработки и старые переписки автоматически не заполняются новыми связями.

Проверка: `python -m pytest backend/tests -q`. Изолированная проверка реального GigaChat без RAG: `verify_notification_pipeline.py --live-model --without-rag --evidence <verified report> --report <output>`. Используется ранее проверенный пример изменения, отдельная временная схема PostgreSQL и закрытый канал Redis; схема удаляется после проверки.

Ранее реализованная цепочка: источник статьи → ссылка в ответе ассистента → сохранённая
связь с вопросом пользователя → изменение этой нормы → уведомление со ссылкой
на прежний чат. Совпадение статьи достаточно для уведомления; GigaChat не
проверяет личное влияние поправки в основном пути.

Текст уведомления: «Изменена норма, использованная в ответе на ваш прежний
вопрос. Возможно, стоит пересмотреть прежний ответ». Это сообщение об
изменении использованного источника. Оно не утверждает появление новых
обязанностей у человека.

В первоначальном варианте для совпадения требовались проверенный каталог источников и явные affected_norms.
Подключены автоматический разбор явных ссылок Consultant и дополнительный
операторский JSON-файл reviewed_changes.json. Автоматический разбор поддерживает
только однозначные ссылки на изменяемые статьи в тексте поправок.
Ниже отдельно описаны текущий путь и сохранённый экспериментальный анализ.

## Как работает

1. `rag_context.build_rag_bundle` выполняет прежний поиск фрагментов и возвращает
   текст контекста вместе с метаданными источников из локального каталога.
2. Источник получает метку `[Источник N]`. NLPService просит ассистента указывать
   такую метку рядом с утверждением, для которого источник использован.
3. `cited_legal_sources` принимает только метки реально предложенных источников.
   Полученный, но не процитированный фрагмент, неизвестная метка и упоминание
   номера статьи без каталога не создают связь.
4. После генерации chat API сохраняет ответ и связи одной транзакцией до
   отправки `[DONE]`. Записываются сообщения пользователя и ассистента,
   идентификатор нормы, источник, редакция, хеш и процитированный фрагмент.
   Проверяется принадлежность обоих сообщений чату текущего пользователя.
   Повторная запись той же нормы для того же ответа не создаёт дубль.
5. Для ответа из кэша ссылки восстанавливаются по меткам из сохранённого текста
   и текущим предложенным источникам. Ключ кэша учитывает идентификаторы норм,
   редакции и хеши источников. Приватные записи связей пользователей в кэш
   ответа не помещаются.
6. JSON-источник изменений может передать явный `affected_norms`. Мониторинг
   сохраняет эти нормы отдельно от документа, которым внесены поправки.
   `find_references_for_change` находит связанные сообщения по нормам.

## Идентификатор нормы

`document_key` — согласованный стабильный ключ исходного правового документа.
Он одинаков в каталоге RAG и в `affected_norms`. Это не номер акта о поправках,
не название файла и не автоматически придуманный моделью идентификатор.
`article`, `part`, `point` — отдельные строки без префиксов «ст.», «ч.» и «п.».
Входные строки очищаются от пробелов по краям, но не угадываются из текста.
Например, `7.1` остаётся отличным от `7`.

Пустое поле означает весь соответствующий уровень: изменение статьи без
части проверяет связи с её частями; связь с целой статьёй подходит для
проверки изменения её конкретного пункта. Разные явно указанные части или
пункты не совпадают. Без статьи нельзя указать подчинённую часть/пункт.
Если точность изменения неизвестна, не заполняйте её догадкой. Норма без
статьи означает известное изменение документа целиком; неизвестный документ
не должен получать фиктивный `document_key`.

## Каталог источников

В `RAG_DOCS_PATH` нужен операторский файл `legal_sources.json`:

```json
{
  "sources": [
    {
      "file": "article_7.txt",
      "document_key": "training:service-rules",
      "article": "7",
      "part": "1",
      "point": "",
      "source_url": "https://example.org/training/service-rules#article-7",
      "revision": "training-v1",
      "sha256": "SHA256 точных байтов article_7.txt"
    }
  ]
}
```

Один файл содержит текст одной указанной нормы. Для файла с несколькими
статьями нельзя указывать произвольную одну статью для всех его фрагментов:
разделите файл по нормам или явно используйте уровень целого документа.
Каталог составляет человек после проверки источника и соответствия текста
указанной норме. Хеш проверяет неизменность предоставленного файла;
он не доказывает юридическую правильность или официальность публикации.
Модель не создаёт и не подтверждает каталог самостоятельно.

Неподходящий хеш, путь вне каталога, неоднозначные записи для одного файла,
отсутствующая редакция или некорректная HTTPS-ссылка исключают файл из
отслеживания норм. Обычный текстовый поиск RAG при этом остаётся доступен.
Индекс RAG кэшируется в процессе: после обновления файлов или каталога
перезапустите backend, чтобы загрузить актуальные фрагменты и метаданные.

В `docs/fixtures/legal_norm_tracking` находится готовый учебный каталог с
настоящим вычисленным хешем и примером `changes.json`. Это вымышленные
правила, не действующее законодательство. В рабочий каталог автоматически
они не добавлялись. Для локального демонстрационного запуска можно задать
RAG_DOCS_PATH равным абсолютному пути этой папки и включить RAG_ENABLED.

## Изменения законодательства

Пример структурированных данных:

```json
{
  "changes": [{
    "title": "Вымышленный акт о поправках",
    "document_number": "TRAINING-AMENDING-1",
    "description": "Изменён срок в статье 7 части 1 учебных правил",
    "affected_norms": [{
      "document_key": "training:service-rules",
      "article": "7",
      "part": "1",
      "point": ""
    }]
  }]
}
```

Эти поля должен предоставлять подготовленный источник с проверенной
разметкой. Парсер проверяет структуру идентификаторов, но не доказывает,
что публикация действительно изменяет указанные нормы. Номер акта о
поправках не подставляется как идентификатор изменяемого закона.

Парсер Consultant сохраняет ссылки на акты, которыми внесены изменения.
Мониторинг автоматически открывает эти ссылки и извлекает явно обозначенные
целевые статьи известных документов. Неподдерживаемые формулировки остаются
без разметки. Старые ответы ассистента автоматически не размечаются.
Ранее сохранённый обзор можно автоматически дополнить подтверждёнными нормами
из той же редакции, без создания нового изменения. Подробности ниже.

## Уведомления об изменении использованной нормы

`dispatch_law_change_notifications` по умолчанию использует явные LawChangeNorm
и `find_references_for_change`. Не требуются ключевые слова, интересы, дополнительные
заявления пользователя или запросы к GigaChat. Все совпавшие ссылки активного
пользователя объединяются в одно уведомление на пару пользователь/изменение.
Разные явно указанные статьи, части и документы не совпадают; пустой уровень
означает весь соответствующий уровень документа.

Уведомление содержит описание поправки, источники и предложение открыть прежний
вопрос. Связанные чаты и нормы передаются в meta. На фронте есть раскрытие полного
текста изменения и ссылки на все связанные чаты. Старые отрицательные решения
GigaChat не блокируют уведомление об изменении использованной статьи.
В основном пути не создаются LawReferenceAssessment с фиктивным verdict=relevant.

LawChangeDelivery сохраняет уникальность пользователь/изменение и метаданные.
Notification и доставка записываются внутри savepoint, Redis получает событие
только после успешного commit. При отказе Redis уведомление доступно через REST;
автоматического replay/outbox нет. Повторный запуск не создаёт дубль.

Сохранено прежнее окно новых изменений — последние два дня по created_at.
Также выбираются старые изменения с ранее сохранёнными недостатком данных/ошибкой
анализа. Автоматической рассылки всей исторической базы или переразметки старых
ответов нет. Уведомления, уже отправленные прежним способом, повторно не отправляются.

Запись без affected_norms пропускается. Прежний keyword-отбор доступен только
при явном legacy_keyword_fallback=True. Celery вызывает функцию без этого флага.

## Сохранённый анализ личного влияния

`check_personal_relevance=True` явно включает прежний дополнительный этап:
анализ поправки GigaChat → проверка каждой связанной ситуации → только подтверждённые
решения. Это экспериментальный режим; Celery по умолчанию его не использует.
Сервисы, таблицы оценок и тесты сохранены для дальнейшей работы, без удаления данных.

Контекст этой проверки содержит исходный вопрос и до десяти сообщений пользователя
до него и после него, всего до 6000 символов. Ответы ассистента не подтверждают
личные обстоятельства. Анализ закона переиспользуется между ситуациями одного
изменения в пределах запуска. Последнее решение записывается в
LawReferenceAssessment; отрицательные решения кэшируются по отпечатку входа,
ошибки повторяются. Смысловая точность этого режима пока не подтверждена.

## Контракт с фронтом

GET /notifications и PATCH /notifications/{id}/read возвращают дополнительное
необязательное поле meta. То же поле приходит через WebSocket:

```json
{
  "notification_basis": "article_change",
  "personal_relevance_checked": false,
  "law_change_id": 1,
  "chat_id": 12,
  "related_chat_ids": [12, 15],
  "reference_ids": [3, 7],
  "norms": [{"document_key": "training:service-rules", "article": "7", "part": "1", "point": ""}],
  "reasons": ["Изменённая норма использовалась в ответе на ваш прежний вопрос."]
}
```

Значения meta сохраняются вместе с доставкой и доступны после перезагрузки
страницы. Store фронта и useNotificationWS сохраняют их после проверки
структуры Zod. Можно использовать chat_id для перехода к основному чату,
related_chat_ids для списка связанных ситуаций. NotificationBell показывает ссылки на связанные чаты и раскрывает
полный текст поправки через «Подробнее об изменении».

Аддитивная миграция 003 следует за 002. В текущем механизме запуска новые
таблицы создаёт Base.metadata.create_all; после обновления сначала следует
запустить backend, затем перезапустить Celery worker/beat. Ни рабочая БД,
ни настоящие Redis-каналы во время реализации не изменялись.

Проверки текущей версии: 195 backend-тестов прошли, 1 пропущен; `npm run build` прошёл
(TypeScript и Vite). В `test_norm_notifications.py` проверяются несколько
ситуаций без интересов, объединение подтверждённых чатов, сохранение
недостатка данных, поздние уточнения к старому изменению, повтор после
HTTP 402, несовместимые статусы, неактивный пользователь, отсутствие

и отправка уведомлений пользователям не выполнялись.


## Тексты редакций из JSON-источника

Импорт принимает необязательные строковые `old_version` и `new_version`
в каждом элементе `changes` и сохраняет их в соответствующие поля LawChange.
Переносы строк сохраняются. Пустые строки и значения другого типа не
используются как текст закона. `description` остаётся отдельным обзором:
если новая редакция отсутствует, обзор больше не записывается в её поле.
GigaChat уже получает описание и обе редакции в анализе изменения.
Редакции и affected_norms должен подготовить и проверить поставщик данных;
импорт не восстанавливает их из краткого обзора Consultant.
Ранее сохранённые записи автоматически не исправляются.

## Подключённый источник точных изменений

Мониторинг сначала читает `reviewed_changes.json` из RAG_DOCS_PATH, если файл
существует, затем обычные HTTP-источники. Создан рабочий пустой файл

В Docker каталог уже смонтирован как /app/rag_docs у API, worker и beat:
новые контейнеры, сервисы и монтирования не требуются. При следующем запуске
обновлённого worker этот стандартный файл подключается без изменения .env.
Каждый цикл мониторинга перечитывает его; дубликаты по заголовку/ссылке не создаются.

Можно задать LAW_CHANGE_CURATED_FILE для другого файла. На Windows используется
абсолютный локальный путь, в Docker — путь внутри контейнера. Секреты и настройки
.env во время реализации не изменялись. Если нужен только локальный источник,
вызов monitor_sources(source_urls=[]) отключает HTTP-запросы; обычный запуск
Celery сохраняет прежний список HTTP-источников.

Формат записи:

```json
{
  "changes": [{
    "reviewed": true,
    "title": "Название публикации о поправке",
    "document_number": "Номер акта о поправках",
    "date": "2026-10-11",
    "description": "Проверенное описание изменения",
    "url": "https://example.org/publication",
    "affected_norms": [{
      "document_key": "Согласованный ключ исходного закона из каталога",
      "article": "7", "part": "1", "point": ""
    }]
  }]
}
```

Это пример структуры, не данные действующего закона. `reviewed=true` ставит
человек после проверки публикации и изменяемых норм; флаг не доказывает саму
юридическую правильность разметки. `document_number` относится к акту о поправках,
а `document_key` — к исходному изменённому документу. old_version/new_version
необязательны; передаются только проверенные тексты, без восстановления моделью.

Перед импортом весь файл проверяется сервисом curated_law_changes:
отметка reviewed должна быть именно true, обязательные строки непустые,
дата корректна, ссылка HTTPS без логина/пароля, хотя бы одна норма указана.
Все её идентификаторы должны совпадать с существующим проверенным каталогом
по документу и совместимому уровню статьи/части/пункта. Файл ограничен 2 МиБ,
список — 1000 изменениями. Неправильная запись отклоняет весь файл до импорта.
Ошибка источника не останавливает сбор обычных HTTP-обзоров. Содержимое файла,
URL с учётными данными и секреты в диагностике не выводятся.

## Контрольное уведомление на PostgreSQL и Redis

backend/verify_notification_pipeline.py выполняет отдельно запускаемую живую
проверку только при явном --live-model. Он создаёт уникальную временную схему
notification_check_<uuid> в PostgreSQL и приватный Redis-канал verification:<uuid>.
Рабочая схема public и пользовательские каналы notifications:<id> не используются
для тестовых данных или публикации. После завершения, включая ошибку, собственная
временная схема удаляется; удаления рабочей базы нет.

Успешный прогон использовал настоящие маршруты FastAPI через ASGITransport,
JWT временного пользователя, реальный GigaChat, PostgreSQL и Redis.
Само изменение взято из уже проверенного живого отчёта
consultant_amendment_resolution.json; это повторное воспроизведение подтверждённой
поправки, а не ещё одна загрузка обзора. Пользователь сообщил свою роль и запросил
ответ по части 16 статьи 4 закона 103-ФЗ с источником. Сохранена одна ссылка на норму.

Результаты: уведомлений создано 1, при повторном запуске 0; Redis-событие получено;
REST вернул chat_id прежнего вопроса; история этого чата доступна владельцу;
другой тестовый пользователь не видит уведомление и получает 404 на чужую историю;
отметка прочтения сохранена. Временная схема удалена. Отчёт:
docs/notification_pipeline_live.json. Тестовое уведомление поэтому не появится
в текущем рабочем аккаунте браузера. Фактический клик браузером в этой проверке
не выполнялся: подтверждены метаданные ссылки и получение истории по API.

Первоначальный более общий вопрос не дал подтверждённой сохранённой ссылки в
контрольном прогоне. Такое отсутствие не является основанием рассылать по словам:
уведомление создаётся только после ответа с реально использованным источником.
Охват произвольных пользовательских вопросов остаётся ограничен RAG и цитированием.

Скрипт не печатает ответы модели, токены или секреты. Запуск --live-model использует
токены GigaChat. Для выполнения внутри API контейнера нужно скопировать скрипт и
проверенный отчёт и задать PYTHONPATH=/app; --report указывает путь безопасного JSON.
Обычный запуск приложения не запускает эту контрольную проверку автоматически.
