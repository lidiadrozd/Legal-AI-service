# Передача уведомлений команде

## Что реализовано

Связь сохраняется по распознаваемой ссылке ассистента: клиент (через владельца чата) → чат → закон → статья, при наличии также часть/пункт. Номер статьи сравнивается вместе с идентификатором закона. Без определённого закона связь для уведомлений не создаётся. Старые переписки автоматически не заполнены такими связями.

Мониторинг разбирает формальные инструкции поправок и может сравнивать сохранённые тексты статей законов, использованных в чатах. Первое получение текста создаёт исходный снимок, а не уведомление. Неопределённая запись о новой редакции из обзора не считается подтверждённым изменением статьи и задерживается.

Уведомления сохраняются в PostgreSQL, доставляются через Redis/WebSocket и доступны через REST. Реализованы защита от повторов, проверка владельца, раскрытие текста и переход в исходный чат. Основной мониторинг — 11:00 Екатеринбурга; условные повторы ошибочных источников — 12:00, 14:00, 17:00.

## Доработки чата и документов 14.10.2026

Консультация и создание документа используют отдельные промпты. Генерация документа требует JSON по существующей схеме; при ошибке формата выполняется одна попытка исправления. Пользовательские запросы, история и вложения передаются как данные, отдельно от системных инструкций. Проверены отказы на посторонние запросы и просьбы раскрыть промпт, но абсолютная защита от всех атак не заявляется.

Исправлено сохранение полного ответа перед передачей потока клиенту и устранены дубли при завершении потока. Новые чаты показываются сверху. Ответы оформлены русскими заголовками; напоминание о возможных ошибках ИИ показано под чатом. Только служебные метки `[Источник N]` скрываются на экране: исходный текст, названия законов, номера статей и связи для уведомлений сохраняются. При пропущенном основании и доступных источниках выполняется одна проверка моделью; использованные подтверждённые нормы получают явную подпись. Неиспользованные найденные статьи автоматически не связываются с клиентом.

Добавлены проверенные фрагменты статей 127 и 140 ТК РФ. Это небольшая база источников, а не полное законодательство. Детали: `document_prompt_verification.md`, `labor_grounding.md`; текущий проверочный отчёт — `citation_basis_live_check.json`. Старые ошибочные ответы автоматически не переписываются.

## Локальный запуск после получения кода

Нужны Docker Desktop с работающим Linux backend, Docker Compose 2.20+ и Node.js/npm.

1. Создать `backend/.env` по `backend/.env.docker.example`; настроить свои реквизиты GigaChat и параметры приложения. Реальный `.env` передавать в GitHub нельзя. Общедоступный CA в `backend/certs` нужен для проверки TLS GigaChat.
2. Из корня проекта выполнить:

```powershell
docker compose up -d --build
docker compose ps
```

API доступен локально на `http://127.0.0.1:8000`. Для уведомлений должны работать и `celery_worker`, и `celery_beat`, а также PostgreSQL и Redis. Не переключаться между запуском из корня и из `backend` для уже работающей установки: имена Compose-проекта и томов могут отличаться.

3. Для фронтенда создать `frontend/.env.local` с `VITE_API_BASE_URL=http://127.0.0.1:8000`, затем в отдельном терминале:

```powershell
cd frontend
npm ci
npm run dev
```

Фронтенд: `http://localhost:3000`.

Новые таблицы зарегистрированы в моделях; API вызывает `Base.metadata.create_all` при старте. Это создаёт отсутствующие таблицы, но не заменяет миграцию существующих столбцов. Перед обновлением существующей серверной БД сделать резервную копию и проверить совместимость её схемы. Не выполнять `docker compose down -v`: это удалит тома с данными.

## GitHub и общий сервер — разные шаги

Актуальный сервер и порядок публикации описаны в [deploy-notes.md](deploy-notes.md). Приведённые выше проверки относятся к истории разработки, а не к подтверждённой конфигурации рабочего сервера.

Изменения нужно перенести в свежий Git-клон общего репозитория, проверить различия с актуальным кодом команды и отправить отдельной веткой через Pull Request. Не переносить `.git`, `.env`, виртуальное окружение, `node_modules`, `backend/storage`, дампы, логи и временные файлы. Не заменять весь репозиторий через ZIP и не использовать force push.

После объединения Pull Request на общем сервере получить изменения и пересобрать сервисы в прежнем Compose-проекте. Фронтенд собрать командой `npm ci` и `npm run build`, затем опубликовать `dist` способом, который уже использует команда. Настроить URL серверного API, не localhost.

Текущий Docker-конфиг публикует API только на `127.0.0.1:8000`; внешний доступ требует существующего reverse proxy или отдельно согласованной настройки публикации. GitHub push сам по себе не развёртывает проект на сервере.
